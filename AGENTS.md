# Правила Проекта Для Codex

Этот репозиторий содержит публичный сайт и публичную документацию Module. Сайт является границей
представления продукта, а не источником истины о runtime-поведении, совместимости или готовности
функций.

## Начальный Маршрут

1. Прочитай этот файл.
2. Открой [`docs/AI_INDEX.md`](docs/AI_INDEX.md) и выбери один маршрут текущей задачи.
3. Читай только относящиеся к задаче source-файлы и документы-владельцы. Не загружай весь проект,
   документацию или соседние `module-*` заранее.
4. Перед изменениями выполни `git status --short -uall` и определи точный scope.

## Постоянные Инварианты

- Новые правила, документацию и человекочитаемый контент пиши на русском, если пользователь не
  попросил иначе. Имена API, типов, файлов, маршрутов, CSS-классов, команд и других технических
  идентификаторов сохраняй в проектном написании.
- Считай все существовавшие до начала работы изменения пользовательскими. Не очищай, не
  сбрасывай, не перезаписывай, не добавляй в индекс и не коммить их без прямой просьбы.
- Запросы на исследование, аудит, review, диагностику, статус или отчёт являются read-only по типу
  задачи. Запрос на реализацию разрешает изменения файлов только в согласованном scope; Git, CI,
  deployment, Figma и другие внешние mutations требуют отдельного явного полномочия.
- Явный read-only режим запрещает создание, изменение, форматирование, переименование и удаление
  файлов, любые Git mutations и изменения внешних систем. Нужные правки перечисляй как deferred
  work.
- PR Completion выключен по умолчанию. Без прямой команды не выполняй `git add`, `git commit`,
  `git push` и не создавай PR. Commit и push в default branch запрещены; merge выполняет
  разработчик.
- Не раскрывай и не сохраняй secrets, tokens, passwords, private keys, OTP/setup codes, реальные
  env values и содержащие их логи в файлах, commits, screenshots или ответах.
- Память агента и исторические записи — только неавторитетный cache. Текущий checkout,
  действующие документы-владельцы, runtime evidence и актуальные внешние источники имеют приоритет.
- Отделяй наблюдаемые факты, инженерные выводы, неизвестное, принятые решения и предлагаемое
  поведение. Не выдавай предложение или частичное доказательство за current product behavior.
- Если новое решение не укладывается в правила или конфликт инструкций нельзя безопасно разрешить,
  останови затронутую часть и вынеси конкретный вопрос разработчику.
- Перед вопросами разработчику сначала исследуй доступные source, config, tests и владельца
  контракта. Не используй вопросы как замену минимальному repository inventory.
- Подтверждённый дефект не должен исчезать в итоговом сообщении: исправь и проверь его в
  согласованном scope либо явно назови как unresolved/deferred work с причиной. Не создавай
  task-файл только ради формальности, пока в проекте нет принятого task workflow.
- Параллельную работу применяй только после явного разрешения и когда есть минимум две независимо
  проверяемые bounded задачи, окупающие coordination overhead. Делегированные полномочия можно
  только сузить; запись в общую рабочую копию выполняется одним владельцем последовательно.
- Вложенный `AGENTS.md` может добавлять локальные owners, команды и более строгие проверки, но не
  может ослаблять защиту dirty worktree, secrets, read-only и publication/external mutation gates.

## Публичный Контент И Источники Истины

- Утверждения о работающем поведении проверяй по текущему implementation owner в профильном
  репозитории Module. Исследования, позиционирование и внешние источники проверяй по актуальным
  владельцам в `module-market-intelligence`; изменяемые внешние факты сопровождай источником и датой
  проверки.
- Явно различай то, что работает сейчас, доступно только в пилоте, планируется или пока не
  подтверждено. Не усиливай маркетинговую формулировку сверх доступного evidence.
- У каждого факта или принятого решения должен быть один основной владелец. Не дублируй большие
  контракты соседних проектов на сайте: делай короткую проекцию и указывай источник, если он нужен
  для сопровождения.
- Не публикуй персональные данные, внутренние адреса, непубличную инфраструктуру и диагностические
  детали, не предназначенные для внешней аудитории.
- `noindex,nofollow`, домен, формы отправки данных, аналитика и production deployment считаются
  отдельными release boundaries. Не включай и не подключай их без явной задачи.

## Код, Интерфейс И Документация

- Сохраняй текущий стек Astro, Starlight и TypeScript. Перед добавлением dependency, abstraction или
  нового UI-паттерна проверь существующие возможности проекта и реальную потребность.
- Именование, форматирование, semantic spacing, control flow, comments, структура Astro/TypeScript
  units и CSS принадлежат [`docs/code-style.md`](docs/code-style.md). Не объявляй manual-review
  правило автоматическим gate, пока в проекте нет соответствующей действующей проверки.
- Тестовая структура, выбор checks и visual/browser evidence принадлежат
  [`docs/testing.md`](docs/testing.md). Изменение поведения должно иметь проверку публичного
  результата; одна успешная сборка не заменяет behavioral или visual evidence.
- Сужай изменение до конкретной страницы, секции, стиля, asset-а или build/config boundary. Не
  выполняй unrelated refactoring и не создавай общую архитектуру под гипотетическое будущее.
- Переиспользуемый код выделяй только после появления реального второго consumer-а или ясной общей
  ответственности. Локальные детали держи рядом с владельцем.
- Используй семантическую HTML-разметку, сохраняй keyboard navigation, видимый focus, reduced
  motion и доступные названия интерактивных элементов. Не ухудшай адаптивность и поддержку ширины
  от `320px`.
- Для визуальных изменений успешная компиляция не доказывает корректность. Если визуальное
  поведение входит в scope, укажи проверенные viewport, состояние и способ сравнения; пропущенную
  browser-проверку назови явно.
- Не редактируй вручную generated output в `dist/` и `.astro/`. Меняй source owner и пересобирай
  штатной командой.
- Публичная документация в `src/content/docs/` обязана описывать подтверждённое поведение,
  ограничения, ручной способ управления и способ проверки результата, когда они применимы.

## Исследование И Изменения В Соседних Проектах

- Соседние `module-*` по умолчанию доступны только для чтения как источники контрактов и evidence.
  Не меняй другой репозиторий без отдельной явной задачи и scope для него.
- В research-pass сначала исследуй exact source, tests, runtime path и владельца контракта. Findings
  и target behavior фиксируй отдельно; не исправляй product code в рамках одного лишь исследования.
- Синхронизацию общих правил выполняй только по явной просьбе. Сравнивай смысл и применимость, а не
  копируй предметные формулировки дословно. Текущий журнал принятия правил:
  [`docs/rules-sync.md`](docs/rules-sync.md).

## Проверки И Завершение

- Используй команды из `package.json` и выбирай минимальный набор по затронутой поверхности.
- Применяй verification matrix из [`docs/testing.md`](docs/testing.md); не запускай неактивные
  branches «на всякий случай».
- Для изменения Astro, TypeScript, конфигурации, стилей или публичного контента основной полный gate
  — `yarn build`; для быстрой статической проверки допустим `yarn check`.
- После изменений документации проверь относительные ссылки и лимит обязательных Markdown
  entrypoints в `20 KiB`. Для всех изменений выполни `git diff --check` и audit фактического
  `git status`/diff.
- Проверка считается зелёной только после успешного завершения. Прерванные, пропущенные и
  неприменимые проверки называй отдельно.
- В финальном отчёте перечисли изменённую область, реально выполненные проверки, оставшиеся риски и
  отложенную работу. Явно укажи, менялась ли production logic или только project instructions/docs.

## CI

- CI диагностируй evidence-first: определи точные workflow, run, attempt, commit и job, затем найди
  первый причинный failure. Отделяй defect репозитория от dependency/install, runner,
  infrastructure и policy failure.
- Не называй CI исправленным без зелёного server-side run. Rerun, cancel, dispatch, изменение
  workflow, secrets, permissions, runner, cache и deployment требуют отдельного разрешения.
- Не переносись в репозиторий полные CI logs. Сохраняй только минимальное обезличенное evidence,
  необходимое для вывода.
