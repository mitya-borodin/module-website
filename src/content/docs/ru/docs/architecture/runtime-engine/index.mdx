Движок связывает события оборудования, команды человека и готовые автоматизации.
Он выбирает момент расчёта, передаёт ему актуальные данные и направляет результат
к устройствам, интерфейсу и хранилищу. Логика освещения при этом отделена от очередей,
транспорта и сохранения состояния.

**Область применения:** движок `MacroRuntimeEngine`, макрос освещения
`MacrosType.LIGHTING`, расчёт `LightingCalculation` версии 15.

## От события устройства до расчёта

Представим, что датчик движения прислал новое значение по MQTT. Сообщение проходит
несколько участников, каждый из которых решает свою задачу.

1. **Отобрать данные и адресатов.** `CollectorFilter` определяет, нужно ли сообщение
   общему сборщику. Независимо от него `Normalizer → ReactionRouter` подготавливает
   наблюдение и выбирает реакции по установленному плану. Общее сообщение проходит дальше,
   если `collector = true` **или** список реакций непуст.
2. **Обновить наблюдаемое состояние.** `Collector` сначала применяет данные к картам
   устройств и контролов и обновляет буфер GUI. Это происходит и для сообщения,
   которое прошло только из-за реакции.
3. **Передать выбранную реакцию.** Через `EventBus` она попадает в `MacroRuntimeEngine`,
   который проверяет экземпляр и поколение и передаёт работу планировщику.
4. **Выполнить расчёт.** Когда очередь доходит до этой работы, `MacroScheduler` вызывает
   адаптер. `MacroSchedulerAdapter` преобразует вызов в предметную команду и передаёт
   расчёту время `nowMs`.
5. **Разделить результаты.** Расчёт возвращает неизменяемые SEND-снимки либо `undefined`.
   Отправка команд и обработка состояния выполняются отдельными компонентами.

Контрол здесь — отдельный канал или значение устройства: например, показание движения
или состояние реле. Наблюдаемое значение и желаемое значение расчёта могут различаться.

`MacroDeviceReader` читает те же актуальные карты Collector, без отдельной копии всех устройств.
При этом наблюдение сохраняет предыдущее и новое значения конкретного события. Расчёт использует
и событие, ради которого его вызвали, и актуальное наблюдаемое состояние остальных привязок.

Оба варианта MQTT backend — JS worker и Rust — используют это разделение отбора данных
и адресной маршрутизации. При `collector = true` сообщение также поступает в прежний
`MacrosEngine`, который обслуживает остальные входные типы и прежние обозначения
макросов освещения. `MacroRuntimeEngine` получает выбранные реакции через `EventBus`.

## Кто за что отвечает

| Компонент | Ответственность |
| --- | --- |
| `MacroRuntimeEngine` | Создаёт и удаляет экземпляры, ведёт их жизненный цикл и поколения конфигурации, устанавливает план MQTT-реакций с подтверждением, обрабатывает пользовательские команды |
| `LightingRuntimeDefinition` | Задаёт особенности типа: начальную подготовку, создание расчёта, проверки и преобразования команд |
| `MacroRuntimeEntry` | Представляет один экземпляр: идентификатор, метаданные, поколение конфигурации и связь с расчётом; создаёт общий адаптер |
| `MacroSchedulerAdapter` | Превращает вызов планировщика в допустимую команду расчёта с `nowMs` |
| `MacroScheduler` | Выбирает готовую работу, управляет очередями, квотами, временем и допуском результата |
| `LightingCalculation` | Применяет настройки и предметные правила освещения к своему состоянию |
| `MacroSendDelivery` | Доставляет готовый снимок в MQTT |
| `MacroStateConsumer` | Последовательно читает JSON состояния, публикует его и сохраняет по установленным правилам |

Для подключения другого типа макроса к общему движку создаются его определение и расчёт.
Очереди, доставка команд и обработка состояния остаются общими.

### Настройки и жизненный цикл

Для нового экземпляра Engine подготавливает расчёт и устанавливает план реакций в MQTT.
Планировщик получает экземпляр после подтверждения установки плана — ACK.
С этого момента входящие наблюдения маршрутизируются по установленному плану.

При замене настроек сначала проверяется новая конфигурация и устанавливается новый план с ACK.
Затем настройки заменяются, тот же адаптер повторно регистрируется в Scheduler,
а конфигурация сохраняется. План периодических задач читается при регистрации;
его не нужно заново получать на каждом расчёте.

Поколение конфигурации (`generation`) позволяет отсечь сообщения от прежних настроек:
MQTT-канал проверяет его до
передачи в Collector, Engine — до допуска работы в Scheduler. Уже принятые задачи используют
текущие настройки. Результаты принимаются только для того же активного экземпляра.

## Как планировщик выбирает работу

У Scheduler шесть классов работы. Он обходит их циклически и использует квоты, заданные
при сборке приложения.

| Класс | Какая работа готова к выполнению | Квота |
| --- | --- | --- |
| `urgent` | Срочные MQTT control и команды GUI | 4 |
| `send` | Начало доставки ранее принятого SEND-снимка | 4 |
| `lifecycle` | `initial` и `resume` | 2 |
| `deadline` | Самая ранняя наступившая периодическая задача | 2 |
| `normal` | Обычные MQTT control | 4 |
| `background` | Следующий активный экземпляр общего круга | 1 |

В каждом классе находится свой вид работы. Пустые классы пропускаются.
Позиция обхода и израсходованная квота сохраняются между
проходами; новое urgent-событие не прерывает начатый расчёт и не запускает обход заново.

### Что означают 8 и 200 миллисекунд

**8 мс — бюджет одного прохода диспетчера.** Проверка выполняется после полного
синхронного шага. Начатый `execute` выполняется целиком. Если после его завершения
бюджет исчерпан, Scheduler уступает управление до следующего прохода.

**200 мс — пауза до следующего участника общего фонового круга.** Она отсчитывается
после фоновой попытки. При нескольких экземплярах фоновая работа выполняется
по очереди; частота обращения к каждому зависит от длины общего круга.

`TimerPort.getDateNow()` даёт время команды и сроков. Монотонное время
`getMonotonicNowMs()` измеряет длительность прохода. У LIGHTING план периодических
задач пуст: временные правила проверяются в полном расчёте, в том числе при `background`.

### Очереди и ошибки

Urgent, normal и команды GUI разделяют `controlCapacity`; у SEND отдельная ёмкость.
При переполнении новый элемент отклоняется, ранее принятые не вытесняются.
Квота считает попытки, включая завершившиеся исключением.

После успешного `execute` для того же активного экземпляра Scheduler принимает SEND,
если есть место, и создаёт `MACRO_STATE_CHANGED`. Сигнал состояния появляется
также при `undefined`, пустом SEND или отказе принять SEND в заполненную очередь.
Это уведомление о завершённом расчёте; JSON состояния может остаться прежним.

Исключение расчёта не создаёт нового SEND или state-сигнала. Уже изменённое состояние
самого расчёта автоматически не откатывается.

## Как исполняется логика освещения

Общий runtime определяет, **когда** вызвать расчёт. `LightingCalculation` определяет,
**что** должно произойти со светом. Команда и конечное числовое `nowMs` входят в один
синхронный `execute`; настройки и состояние принадлежат самому расчёту.

`initial` сразу переходит к финальному `LightingOutput`: он согласует выходы
с сохранённым состоянием, не выполняя обычную цепочку предметных стадий.

Для остальных принятых команд выполняются следующие действия:

1. **Проверка команды.** Control проверяется по ключу и адресу. Для public-state сначала
   проверяется полный JSON, затем допустимый путь изменения.
2. **SensorData и DerivedState.** Собираются данные датчиков и вычисляются условия,
   необходимые для принятия решения.
3. **Force.** Если принудительный режим применён, расчёт сразу переходит к итоговому
   DerivedState и Output, пропуская ручную, сенсорную и временную логику даже без изменения цели.
4. **ManualAction и SensorAutomation.** Ручная стадия обрабатывает только control.
   Если она изменила свет, сенсорная стадия пропускается. В остальных случаях
   выполняется SensorAutomation.
5. **TimeRules и итоговый DerivedState.** Без применённого Force временные правила
   выполняются и после ручного изменения. Затем пересчитываются итоговые условия.
6. **LightingOutput.** Итоговая цель сравнивается с актуальным reader.

Стадии меняют внутреннее состояние и не отправляют промежуточные команды.
Финальный Output формирует один неизменяемый SEND-снимок с `hardwareOutput` и `messageOutput`,
если есть расхождения виртуальных controls или физические команды.
Если выходы уже согласованы, возвращается `undefined`.
Сверка выходов сравнивает значения контролов и физические команды; метаданные
устройства в это сравнение не входят.

Для public-state допустим путь `['force', 'switch']`. Он запускает полный расчёт
**даже при совпадении нового значения с текущим**. Неподдерживаемый путь возвращает
`undefined`; некорректный JSON состояния вызывает исключение. Неизвестная команда
или неконечное `nowMs` также считаются ошибкой.

## Команды устройствам и состояние

### SEND доставляется отдельно

Scheduler помещает результат в SEND FIFO и вызывает `MacroSendDelivery` в отдельном
send-слоте. Сначала передаются метаданные устройства и контролов, затем значения и
физические команды в порядке снимка. Актуальные адреса записи читаются заново при доставке.
При `isReadOnly` доставка сразу завершается без публикации.

FIFO определяет **порядок начала доставок**. Асинхронный Promise не блокирует следующий
send-слот, поэтому порядок завершения таких Promise может отличаться.
Первая ошибка транспорта прекращает отправку оставшейся части снимка.
Автоматический повтор этой доставки отсутствует.

Отправленный SEND не меняет наблюдаемые controls. Новое значение должно прийти обратно
через MQTT. Если следующий полный расчёт LIGHTING видит прежнее расхождение, он может
снова предложить ту же цель. Так расчёт повторно согласует желаемое состояние
с наблюдаемым, пока обновлённое значение не вернётся через MQTT.

### Состояние читается в своей очереди

Сигнал состояния содержит идентификатор экземпляра. Engine передаёт связь с его
состоянием (`stateBinding`) в `MacroStateConsumer`. Компонент читает актуальный JSON
**при обработке очереди**.

Путь публикации проходит через **Consumer → callback Entry → Engine → EventBus →
MacroRuntimePublisher → GUI**. Engine публикует состояние при активной подписке.
При публикации и сохранении одной записи используется тот же
прочитанный JSON.

Автоматическое сохранение выполняется при `isSaveState && !dryRun`.
После успешной команды GUI Engine отдельно ожидает явного сохранения независимо от
`isSaveState`. В режиме `dryRun` такая GUI-команда отклоняется до `execute`.

Планировщик завершает команду после успешного расчёта для активного экземпляра.
SEND и состояние продолжают обрабатываться в своих очередях. Engine дополнительно
ожидает сохранения, предусмотренного командой GUI. Наблюдаемое значение устройства
система получает отдельным сообщением MQTT.
