Один writer. ROI: источники поведения, подписи и изображения тесно связаны; делегирование не
оправдывает координацию и отдельно не разрешено. Последовательность: source review → текст и

## Редакционные решения

- Сначала три понятных результата, затем вода, электричество, газ, тепло и сравнение интенсивности.
  Горячая/холодная вода показаны в одной сцене с двумя независимыми приборами.
- Учёт линии не представлен как автоматическое определение расхода каждого прибора. Отдельный
  потребитель виден отдельно при собственном измерении.
- Для тепла источник — импульсный выход энергии теплосчётчика, не объём обычного водосчётчика.
- Скорость прямо названа расчётной. Точность зависит от переключений, редкие сигналы могут давать
  ноль до физической остановки; отсутствие сигнала не доказывает отсутствие расхода или исправность связи.
- Количество импульсов, режим времени работы и все поля настройки не развёрнуты в отдельные
  сценарии: авторский scope — ресурсы и скорость расхода. `WORK_TIME` имеет другой алгоритм.
- Нет обещаний архива по дням, тарифов, автоматических отчётов, уведомлений, детекции утечки или
  перекрытия по превышению. Возможные downstream-сценарии обозначены как отдельные связки.
- Иллюстрации статические; [задача анимаций](../../module-market-intelligence/internet-promotion/spec/scenario-animations-brief.md)
  ими не закрывается. Изображения не являются монтажными схемами и аппаратным evidence.

## Открытые инженерные границы

Нормализация legacy units, schema/runtime validation, `FRONT/BACK` speed timing, zero delta,
runtime rebind и lifecycle/persistence gaps остаются у backend owner. Эта редакционная задача
их не исправляет. Для готового решения требуется конкретный счётчик и контроллер, подтверждение
передачи переходов без потерь, цены импульса и единиц, сверка amount и speed на слабом/сильном
расходе, пауза и восстановление после перебоя. Не переносить иллюстрацию в обещание точности
или коммерческого учёта без отдельного evidence.
